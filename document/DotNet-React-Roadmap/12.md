# Chặng 12: React và TypeScript sâu hơn

Thời lượng tham khảo: 4–5 tuần. Điều kiện vào: đã có React app gọi được API ở Chặng 7 và API đã có filter/ownership/concurrency.

Mục tiêu là quản lý state và request bất đồng bộ sao cho UI không hiển thị dữ liệu cũ, không có state mâu thuẫn và vẫn dùng được bằng bàn phím. Không thêm Redux/query library chỉ vì thấy project lớn; trước hết phải mô tả pain point.

## Mục tiêu đạt được

- Thiết kế state shape tránh duplicate và impossible state.
- Dùng reducer cho state transition có nhiều hành động; viết custom hook cho behavior có thể tái sử dụng.
- Phân biệt UI/client state với server state và cache.
- Đồng bộ filter với URLSearchParams.
- Hủy request cũ, xử lý response về ngược thứ tự và hiển thị lỗi đúng.
- Xây form accessible và đo render/performance trước khi tối ưu.

## Tuần 1: state structure và reducer

### Buổi 1: state nào nên tồn tại?

Không lưu cả danh sách đã lọc, tổng tiền và filter nếu có thể tính từ nguồn chính. State tối thiểu có thể là items, filter, status và error; total/visibleItems là derived data.

Tránh các state mâu thuẫn như isLoading = true cùng error != null nếu mô hình UI không cho phép. Có thể dùng discriminated union:

```typescript
type LoadState<T> =
  | { kind: "idle" }
  | { kind: "loading" }
  | { kind: "success"; data: T }
  | { kind: "error"; message: string };
```

Bài tập: vẽ state machine cho load/list/create/update/delete. Mỗi action phải có state hợp lệ; không chữa state bằng nhiều setState rải rác.

### Buổi 2: useReducer và custom hook

```tsx
type ExpenseAction =
  | { type: "loaded"; items: Expense[] }
  | { type: "added"; item: Expense }
  | { type: "removed"; id: number }
  | { type: "failed"; message: string };

function expenseReducer(
  state: Expense[],
  action: ExpenseAction,
): Expense[] {
  switch (action.type) {
    case "loaded":
      return action.items;
    case "added":
      return [action.item, ...state];
    case "removed":
      return state.filter(item => item.id !== action.id);
    case "failed":
      return state;
  }
}
```

Nếu reducer cần error/loading, tạo state object có shape rõ thay vì nhét error vào mảng. Custom hook useExpenses nên che việc fetch/parse/cancel, còn component tập trung vào layout và event.

Bài tập: chuyển list hiện tại từ nhiều setter sang reducer; viết test cho từng action mà không render browser.

## Tuần 2: server state, cache và URL

### Buổi 3: client state khác server state

Filter mở/đóng panel, input chưa submit và theme là UI state. Danh sách expense từ API có freshness, loading, error, refetch và invalidation; đó là server state.

Khi chưa dùng thư viện cache:

- Có một source of truth cho items.
- Sau create/update/delete, cập nhật cache bằng response server hoặc refetch có chủ đích.
- Không optimistic update nếu chưa định nghĩa rollback.
- Nếu có nhiều page/component cùng dùng dữ liệu, ghi rõ cache key và invalidation rule.

Khi project đủ phức tạp, có thể học TanStack Query sau khi cụ giải thích được query key, stale data, invalidation và mutation error.

### Buổi 4: filter chia sẻ qua URL

Dùng URLSearchParams cho from, to, categoryId, page và search text. Refresh hoặc gửi link cho người khác vẫn giữ filter. Validate input URL trước khi gọi API; pageSize do client gửi phải bị giới hạn ở server.

Bài tập: /expenses?from=2026-09-01&categoryId=2&page=1 mở đúng trạng thái. Nút reset xóa các param không cần thiết. Back/forward của browser khôi phục filter.

## Tuần 3: race condition và form

### Buổi 5: request về ngược thứ tự

Khi người dùng gõ nhanh, request cho từ khóa cũ có thể về sau request mới. AbortController giúp hủy request còn chờ, nhưng vẫn cần bỏ qua lỗi abort và không cập nhật state sau khi request không còn là request hiện tại.

```typescript
useEffect(() => {
  const controller = new AbortController();
  const params = new URLSearchParams({ q: searchText });

  setState({ kind: "loading" });

  fetch(apiBase + "/api/expenses/search?" + params, {
    signal: controller.signal,
  })
    .then(response => {
      if (!response.ok) throw new Error("API " + response.status);
      return response.json() as Promise<unknown>;
    })
    .then(value => setState(parseExpenseLoadState(value)))
    .catch(error => {
      if (error instanceof DOMException && error.name === "AbortError") {
        return;
      }
      setState({ kind: "error", message: "Không tải được dữ liệu" });
    });

  return () => controller.abort();
}, [apiBase, searchText]);
```

Debounce có thể giảm số request nhưng không thay thế server validation hoặc race protection. Bài tập: log request id, gõ nhanh, bật throttling và chứng minh response cũ không ghi đè kết quả mới.

### Buổi 6: form và accessibility

Form cần label, focus sau lỗi, thông báo lỗi gắn với field, keyboard flow và button type đúng. Không chỉ đổi màu border để báo lỗi; screen reader cũng phải nhận được.

Checklist:

- label liên kết input bằng for/id hoặc input nằm trong label.
- aria-describedby trỏ đến message tương ứng.
- aria-invalid phản ánh state lỗi.
- submit button có trạng thái disabled/loading nhưng không làm mất thông báo.
- amount/date được kiểm tra cả client và server.
- thông báo success/error có vùng live phù hợp, không tự biến mất trước khi đọc.

## Tuần 4: hiệu năng có đo lường

### Buổi 7: render và memoization

Component render lại khi state/props/context liên quan thay đổi. Đừng dùng memo/useMemo/useCallback hàng loạt trước khi đo. Tìm render thừa bằng React DevTools Profiler; tối ưu data shape, component boundary hoặc list virtualization khi có bằng chứng.

Bài tập: tạo 1.000 expense giả, đo list render, sau đó thử tách row/memo hoặc phân trang. Ghi rõ thay đổi nào cải thiện và trade-off đọc code.

## Dự án chặng: filter, search và mutation ổn định

1. Đưa filter vào URL.
2. Tạo reducer/hook quản lý load, success, error, mutation.
3. Search có AbortController và bỏ qua response cũ.
4. Create/update/delete dùng response chuẩn; xử lý 400, 401, 403, 409 và mạng lỗi.
5. Sau mutation, cập nhật hoặc invalidate cache đúng key.
6. Thêm focus/error/keyboard accessibility.
7. Đo một màn hình chậm trước và sau, không kết luận từ cảm giác.

### Dữ liệu biên bắt buộc

- URL thiếu/sai ngày, categoryId âm, page quá lớn.
- Search rỗng, gõ nhanh, mất mạng, response về ngược thứ tự.
- POST trả 400, 401, 403, 409, 500.
- User bấm submit hai lần, click delete khi row đã biến mất.
- Keyboard-only, zoom 200%, màn hình đọc được thông báo lỗi.
- Danh sách rỗng, một row, 1.000 row.

### Checkpoint

Cụ đạt chặng khi có thể:

- Vẽ state machine và chỉ ra source of truth.
- Gửi link URL filter rồi mở ở tab khác vẫn ra cùng kết quả.
- Tái hiện stale response và chứng minh bản sửa không hiển thị dữ liệu cũ.
- Xử lý được conflict 409 từ Chặng 10.
- Kiểm tra được form bằng bàn phím và giải thích thay đổi performance bằng số đo.
