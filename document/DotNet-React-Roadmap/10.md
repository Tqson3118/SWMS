# Chặng 10: SQL và EF Core sâu hơn

Thời lượng tham khảo: 4–5 tuần. Điều kiện vào: đã có API CRUD, migration và contract ExpenseResponse ở Chặng 5–7.

Chặng này chuyển từ “query trả kết quả” sang “query có thể giải thích, đo lường và giữ dữ liệu đúng khi nhiều người cùng sửa”. Không tối ưu bằng cảm giác; luôn tạo dữ liệu thử, đo trước, thay đổi một thứ rồi đo lại.

## Mục tiêu đạt được

- Đọc execution plan ở mức đủ để tìm scan, seek, join và sort đáng chú ý.
- Tạo index theo query thực tế, không tạo index cho mọi column.
- Hiểu transaction boundary, isolation và nguy cơ đọc dữ liệu chưa ổn định.
- Xử lý optimistic concurrency và trả 409 khi bản ghi đã bị người khác sửa.
- Dùng projection, no-tracking, pagination và query filter có chủ đích.
- Tạo migration an toàn khi database đã có dữ liệu.

## Tuần 1: index và đo query

### Buổi 1: index không phải thuốc chữa mọi query

Index giúp database tìm row theo một số access pattern nhanh hơn nhưng làm tăng chi phí ghi và dung lượng. Query phải lọc/sắp xếp theo cột phù hợp; một index không được dùng chỉ vì nó tồn tại.

Bắt đầu bằng query danh sách theo user và ngày:

```sql
SELECT Id, CategoryId, Amount, SpentOn, Note
FROM Expenses
WHERE OwnerUserId = @ownerUserId
  AND SpentOn >= @from
  AND SpentOn < @to
ORDER BY SpentOn DESC, Id DESC;
```

Tạo dữ liệu thử đủ lớn rồi đo:

```sql
SET STATISTICS IO ON;
SET STATISTICS TIME ON;

-- Chạy query trước khi thêm index.
-- Tạo index dựa trên query và kiểm tra lại execution plan.
```

Bài tập: ghi logical reads, elapsed time và execution plan trước/sau. Nếu dữ liệu quá ít khiến kết quả không có ý nghĩa, nói rõ giới hạn của phép đo.

### Buổi 2: projection, pagination và N+1

API list không nên trả entity/navigation graph không cần thiết. Chỉ chọn field cần hiển thị, áp dụng filter ở database và giới hạn page size do client gửi.

```csharp
var pageSize = Math.Clamp(request.PageSize, 1, 100);
var page = Math.Max(request.Page, 1);

var items = await db.Expenses
    .AsNoTracking()
    .Where(x => x.OwnerUserId == ownerUserId)
    .OrderByDescending(x => x.SpentOn)
    .ThenByDescending(x => x.Id)
    .Skip((page - 1) * pageSize)
    .Take(pageSize)
    .Select(x => new ExpenseResponse
    {
        Id = x.Id,
        CategoryId = x.CategoryId,
        CategoryName = x.Category.Name,
        Amount = x.Amount,
        SpentOn = x.SpentOn,
        Note = x.Note
    })
    .ToListAsync(cancellationToken);
```

Bài tập: thử gọi endpoint với pageSize âm, rất lớn và page overflow. Trả metadata total/page/pageSize rõ ràng. Không gọi ToList trước Where/Skip/Take.

## Tuần 2: transaction và isolation

### Buổi 3: transaction boundary

Một request có nhiều thay đổi liên quan phải xác định ranh giới nguyên tử. SaveChanges thường có transaction cho chính lần save, nhưng một quy trình gồm nhiều lệnh hoặc nhiều SaveChanges cần thiết kế rõ.

```csharp
await using var transaction =
    await db.Database.BeginTransactionAsync(cancellationToken);

try
{
    // Thay đổi expense và audit record phải cùng thành công hoặc cùng thất bại.
    await db.SaveChangesAsync(cancellationToken);
    await transaction.CommitAsync(cancellationToken);
}
catch
{
    await transaction.RollbackAsync(cancellationToken);
    throw;
}
```

Isolation level ảnh hưởng việc transaction nhìn thấy thay đổi của transaction khác. Không học thuộc “Serializable luôn tốt hơn”; mức cô lập cao hơn có thể tăng khóa/chờ. Tạo hai session SQL để quan sát dirty read, non-repeatable read hoặc deadlock ở dữ liệu học tập.

### Buổi 4: migration khi đã có dữ liệu

Trước migration:

1. Backup database học tập hoặc tạo bản copy.
2. Đọc SQL migration sinh ra.
3. Xác định column mới có nullable/default/backfill hay không.
4. Chạy trên database test trước.
5. Có kế hoạch rollback; không xóa migration đã áp dụng chỉ để làm lịch sử “đẹp”.

Bài tập: thêm OwnerUserId hoặc CreatedAtUtc vào database đã có expense. Nếu column bắt buộc, phải backfill dữ liệu cũ trước khi đặt NOT NULL. Kiểm tra số row trước/sau.

## Tuần 3: optimistic concurrency

### Buổi 5: phát hiện hai người sửa cùng row

Optimistic concurrency cho phép nhiều người đọc, nhưng lúc ghi phải kiểm tra bản ghi chưa bị đổi. Với SQL Server, có thể dùng rowversion làm concurrency token.

```csharp
public sealed class Expense
{
    public int Id { get; set; }
    public decimal Amount { get; set; }
    public byte[] Version { get; set; } = Array.Empty<byte>();
}

protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Expense>()
        .Property(x => x.Version)
        .IsRowVersion();
}
```

Khi SaveChangesAsync ném DbUpdateConcurrencyException, không tự động ghi đè dữ liệu mới. Đọc lại current database values, trả 409 Conflict và cho UI lựa chọn tải lại hoặc hiển thị hai phiên bản.

```csharp
try
{
    await db.SaveChangesAsync(cancellationToken);
}
catch (DbUpdateConcurrencyException)
{
    return Conflict(new
    {
        code = "expense_changed",
        message = "Khoản chi đã thay đổi. Hãy tải lại trước khi lưu."
    });
}
```

Bài tập: mở hai cửa sổ hoặc viết hai test scope. Cả hai đọc cùng Version; request thứ nhất lưu thành công, request thứ hai phải nhận 409 và không làm mất dữ liệu thứ nhất.

## Dự án chặng: query nhanh hơn và giữ dữ liệu đúng

Nâng cấp Sổ chi tiêu theo lát cắt:

1. Thêm pagination/filter theo owner và khoảng ngày.
2. Thêm index phục vụ đúng query list đã đo.
3. Thêm báo cáo tổng theo tháng bằng projection/grouping.
4. Thêm rowversion và API cập nhật có concurrency token.
5. Trả 409 có contract ổn định; frontend hiển thị nút tải lại.
6. Viết migration nâng schema trên database có dữ liệu mẫu.
7. Ghi kết quả đo trước/sau trong README, kèm dữ liệu và query đã dùng.

### Dữ liệu biên bắt buộc

- Không có row, page vượt quá total, pageSize 0/101/giá trị rất lớn.
- Hai request cùng sửa một expense.
- Migration chạy trên database rỗng và database đã có row.
- Query filter ngày ở ranh giới đầu/cuối tháng.
- Category bị xóa hoặc không còn hợp lệ.
- Transaction thất bại giữa chừng và audit record không được ghi riêng lẻ.

### Checkpoint

Cụ đạt chặng khi có thể:

- Đọc được lý do query chậm từ SQL/plan/log, không chỉ nói “EF chậm”.
- Chứng minh index giúp một query cụ thể hoặc giải thích vì sao optimizer không dùng nó.
- Tái hiện concurrency conflict và trả 409 mà không mất update.
- Nâng schema mà giữ được dữ liệu cũ và có cách kiểm tra.

5. Transaction và optimistic concurrency giải quyết hai loại vấn đề nào?
