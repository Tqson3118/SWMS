# Chặng 11: API nhiều người dùng và bảo mật

Thời lượng tham khảo: 4–5 tuần. Điều kiện vào: đã có owner/concurrency model hoặc ít nhất hiểu vì sao ID trên URL không phải quyền truy cập.

Mục tiêu của chặng này là bảo vệ dữ liệu theo người dùng và giảm các lỗi bảo mật phổ biến. Không tự viết thuật toán mật mã, không tự xây hệ thống identity từ đầu và không coi CORS là cơ chế phân quyền.

## Mục tiêu đạt được

- Phân biệt authentication: ai đang gọi, với authorization: họ được phép làm gì.
- Bảo vệ resource theo user ownership ở mọi query và command.
- Dùng policy/resource-based authorization thay vì chỉ kiểm tra một role trong controller.
- Hiểu cookie/bearer token, CSRF/XSS và trade-off storage ở mức đủ để chọn cách triển khai.
- Quản lý secret ngoài source; validate input; giới hạn tốc độ; thiết kế idempotency cho request tạo dữ liệu.
- Viết test chứng minh User A không thể đọc/sửa dữ liệu của User B.

## Tuần 1: identity và ownership

### Buổi 1: authentication flow

Vẽ flow trước khi code:

1. User gửi credential qua kênh HTTPS.
2. Hệ thống xác thực và tạo session/token theo cơ chế đã chọn.
3. Request tiếp theo mang credential.
4. middleware xây ClaimsPrincipal.
5. endpoint dùng identity để quyết định quyền trên resource.

Cookie và bearer token không phải hai từ đồng nghĩa. Cookie thường được browser gửi tự động nên cần hiểu CSRF; bearer token cần bảo vệ khỏi việc bị đánh cắp và không nên đặt vào nơi dễ bị script đọc một cách tùy tiện. Với project học, chọn một flow nhất quán và ghi rõ threat model.

Không log password, access token, refresh token hoặc full request body nhạy cảm.

### Buổi 2: owner filter là điều kiện bắt buộc

Nếu Expense có OwnerUserId, mọi đường đọc/sửa/xóa phải gắn owner vào query hoặc authorization resource. Không tải row theo ID trước rồi mới “nhớ” kiểm tra owner ở một nhánh khác.

```csharp
var userId = User.FindFirstValue(ClaimTypes.NameIdentifier);

if (userId is null)
{
    return Unauthorized();
}

var expense = await db.Expenses
    .SingleOrDefaultAsync(
        x => x.Id == id && x.OwnerUserId == userId,
        cancellationToken);

if (expense is null)
{
    return NotFound();
}
```

Trả 404 cho resource không thuộc user có thể tránh làm lộ sự tồn tại của ID. Quy ước cần nhất quán và được test; đừng để một endpoint trả 403 còn endpoint khác trả 404 mà không có lý do.

## Tuần 2: policy và resource-based authorization

### Buổi 3: policy không thay thế resource check

Role hoặc policy có thể trả lời “user có quyền sửa expense nói chung không”. Nó chưa trả lời “expense cụ thể này có thuộc user không”. Resource-based authorization xử lý quyết định phụ thuộc vào object đang được truy cập.

Các bước học:

1. Xác định claim/user identity.
2. Load resource theo cách không lộ dữ liệu ngoài quyền.
3. Gọi authorization service với resource.
4. Trả 403/404 theo contract đã chọn.
5. Viết test cho owner, user khác và anonymous.

Bài tập: tạo policy CanManageExpenses cho quyền chung, sau đó thêm owner check cho resource. Thử đổi ID trên URL, đổi body OwnerUserId và bỏ claim.

### Buổi 4: input và response contract

Client không được tự gửi OwnerUserId để giành quyền sở hữu. Server lấy owner từ identity. DTO create/update chỉ nhận field người dùng thực sự được phép thay đổi.

Validation cần có nhiều lớp:

- Type/format binding ở API.
- Quy tắc field: amount, date, category.
- Quy tắc resource: category tồn tại, expense thuộc user.
- Database constraint là lớp cuối, không phải lý do bỏ validation.

Không trả entity có navigation/property nội bộ. Error response không chứa stack trace, SQL hoặc secret.

## Tuần 3: web threats và request safety

### Buổi 5: CORS, CSRF và XSS

- CORS là chính sách browser cho cross-origin request; nó không bảo vệ API khỏi một client khác gọi trực tiếp.
- CSRF liên quan request được browser gửi kèm credential tự động; cookie-based flow cần anti-forgery strategy phù hợp.
- XSS xảy ra khi dữ liệu không tin cậy được đưa vào HTML/JS theo cách nguy hiểm; React escape text mặc định nhưng không biến mọi API HTML/URL thành an toàn.
- Không dùng dangerouslySetInnerHTML với dữ liệu người dùng nếu chưa có lý do và sanitizer phù hợp.
- CORS phải ghi rõ origin cần thiết; không dùng wildcard để che lỗi cấu hình.

Bài tập: lập bảng threat → điều kiện → biện pháp → test. Chỉ đưa origin frontend dev thật vào policy, tách dev/staging/production.

### Buổi 6: secret, rate limiting và idempotency

Secret phải nằm trong secret manager/biến môi trường phù hợp, không commit appsettings có password và không đưa secret vào VITE_ frontend.

Rate limiting bảo vệ tài nguyên khỏi lạm dụng, nhưng không thay authentication/authorization. Chọn limit theo endpoint; login/import/report có thể có cost khác nhau.

Idempotency dùng khi client có thể retry do timeout nhưng không muốn tạo trùng. Với POST import hoặc tạo expense:

1. Client gửi Idempotency-Key.
2. Server lưu key cùng owner, request fingerprint và kết quả.
3. Cùng key + cùng payload trả lại kết quả cũ.
4. Cùng key + payload khác trả conflict.
5. Có expiry/cleanup và không dùng key toàn cục giữa user.

Bài tập: bấm gửi hai lần và mô phỏng retry sau khi server đã ghi nhưng response bị mất. Chứng minh database chỉ có một giao dịch hợp lệ.

## Dự án chặng: multi-user Expense Tracker

Nâng cấp theo lát cắt:

1. Tạo user test A và B bằng cơ chế identity đã chọn.
2. Thêm OwnerUserId cho Expense và migration/backfill rõ ràng.
3. Tất cả GET/POST/PUT/DELETE chỉ tác động lên owner hiện tại.
4. Thêm policy quyền chung và resource-based authorization.
5. Thêm 401/403/404 contract theo quy ước.
6. Thêm validation DTO, CORS origin cụ thể, rate limit cho endpoint nhạy cảm.
7. Thêm Idempotency-Key cho create/import.
8. Viết threat model ngắn và test matrix.

### Dữ liệu biên bắt buộc

- Anonymous, authenticated nhưng thiếu claim, user đúng owner, user khác owner.
- Đổi ID trên URL, đổi OwnerUserId trong body, gửi category không thuộc quyền.
- Token/cookie hết hạn, credential sai, replay request.
- Hai request cùng Idempotency-Key nhưng payload khác.
- Origin hợp lệ, origin lạ, preflight bị từ chối.
- Input dài bất thường, HTML/script trong note, amount/date sai.

### Checkpoint

Cụ đạt chặng khi có thể:

- Chứng minh User A không đọc/sửa/xóa được expense của User B kể cả khi biết ID.
- Giải thích vì sao CORS không phải authorization.
- Nêu threat model của flow cookie hoặc bearer token đã chọn.
- Gửi lại request mà không tạo giao dịch trùng.
- Không còn secret thật trong source, log hoặc frontend bundle.

## Interview checkpoint

1. Authentication và authorization khác nhau ở bước nào?
2. Vì sao đăng nhập rồi vẫn chưa được sửa bản ghi này?
3. Tại sao chỉ dùng [Authorize] chưa đủ để bảo vệ resource?
4. Cookie và bearer token tạo threat nào khác nhau?
5. CORS có ngăn Postman gọi API không?
6. Khi nào trả 401, 403 và 404?
7. Idempotency-Key giải quyết timeout/retry như thế nào?
8. Vì sao không nhận OwnerUserId từ client?
9. React escape text có loại bỏ mọi XSS không?

Bài debug có thời gian 40 phút: User B đổi ID trên PUT và sửa được expense của User A. Cụ phải viết test tái hiện, tìm query thiếu owner filter, sửa, rồi chạy lại test regression.

## Tự chấm

- 0: biết các từ authentication/CORS/JWT nhưng chưa bảo vệ resource.
- 1: endpoint có login nhưng ownership còn thủ công, thiếu test.
- 2: owner/policy/error/idempotency chạy được và có test negative.
- 3: giải thích được threat model, trade-off token/cookie và chứng minh bằng request/test.
