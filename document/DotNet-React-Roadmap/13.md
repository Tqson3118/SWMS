# Chặng 13: Kiểm thử có hệ thống

Thời lượng tham khảo: 4 tuần. Điều kiện vào: đã có behavior đáng kiểm thử từ Chặng 8–12.

Không đợi đến chặng này mới bắt đầu test. Từ Chặng 8, mỗi parser, report, validation rule hoặc bug fix nên có test nhỏ. Chặng 13 hệ thống hóa test pyramid, test boundary và CI để cụ có bằng chứng trước khi sửa hoặc deploy.

## Mục tiêu đạt được

- Chọn unit, integration hay end-to-end theo boundary cần chứng minh.
- Viết test theo behavior, không khóa chặt implementation detail.
- Dùng test double có lý do; ưu tiên real implementation hoặc fake đơn giản.
- Tạo database test cô lập và dọn state giữa các test.
- Kiểm thử ownership, validation, concurrency và idempotency.
- Chạy test trong CI và hiểu một lần test fail cần điều tra từ đâu.

## Tuần 1: test pyramid và unit test

### Buổi 1: test đang chứng minh điều gì?

- Unit test: function/pure use case, nhanh, không network/database.
- Integration test: nhiều component và boundary thật, ví dụ API + database test.
- End-to-end: flow người dùng qua browser, ít hơn nhưng bao phủ đường đi quan trọng.

Không đặt mục tiêu phần trăm coverage duy nhất. Một test không assert behavior có thể làm coverage tăng nhưng confidence không tăng.

### Buổi 2: unit test cho import/report/validation

Test theo Arrange–Act–Assert và tên mô tả hành vi.

```csharp
[Fact]
public void CalculateMonthlyTotal_ignores_negative_input_rejected_by_validation()
{
    var items = new[]
    {
        new ExpenseResponse
        {
            Id = 1,
            Amount = 120_000m,
            SpentOn = new DateOnly(2026, 9, 1)
        },
        new ExpenseResponse
        {
            Id = 2,
            Amount = 80_000m,
            SpentOn = new DateOnly(2026, 9, 2)
        }
    };

    var result = new MonthlyExpenseReport().Calculate(items);

    Assert.Equal(200_000m, result.Total);
}
```

Đoạn trên là ví dụ behavior; khi code thật thay implementation, test vẫn nên còn giá trị. Bổ sung test amount âm ở boundary validation thay vì bắt report tự đoán mọi input bẩn.

Bài tập: viết test cho parser CSV, empty file, malformed row, cancellation và report theo category. Mỗi test chỉ nên kể một câu chuyện rõ.

## Tuần 2: integration và database test

### Buổi 3: API integration test

Integration test phải khởi động phần đủ lớn để chứng minh route, binding, authorization, EF và response contract. Dùng test host/database cô lập; không chạy test trên database người dùng.

Các case tối thiểu:

- GET danh sách trả đúng DTO.
- POST hợp lệ trả 201 và Location/body.
- DTO sai trả 400.
- ID không tồn tại trả 404.
- anonymous trả 401.
- user khác owner không đọc/sửa được.
- concurrency conflict trả 409.
- gửi lại Idempotency-Key không tạo row thứ hai.

Nếu dùng WebApplicationFactory, cấu hình database test và seed data trong fixture. Không để test phụ thuộc thứ tự chạy.

### Buổi 4: test double và isolation

Ưu tiên:

1. Real implementation khi nhanh và deterministic.
2. Fake cho database/service đơn giản.
3. Stub cho dữ liệu canned ở boundary.
4. Mock chỉ khi dependency khó kiểm soát hoặc side effect đắt.

Không mock EF Core query đến mức test chỉ chứng minh mock được gọi. Một query quan trọng cần integration test với provider/database phù hợp.

Mỗi test phải tự tạo state cần thiết và dọn state sau đó. Test chạy riêng và chạy cả suite phải cho cùng kết quả.

## Tuần 3: frontend và end-to-end

### Buổi 5: component behavior

Test component bằng input/click và kết quả người dùng thấy:

- loading/empty/error/success.
- form validation và focus.
- submit disable khi đang gửi.
- 409 hiển thị lựa chọn tải lại.
- filter URL giữ đúng sau refresh.

Không test implementation detail như component có đúng bao nhiêu lần gọi setter. Nếu cần kiểm tra request, kiểm tra boundary client/server bằng mock handler hoặc integration test phù hợp.

### Buổi 6: critical E2E flow

Chỉ chọn flow quan trọng:

1. Mở app.
2. Đăng nhập user A.
3. Tạo expense.
4. Lọc theo tháng/danh mục.
5. Sửa hoặc xóa.
6. Đăng nhập user B và xác nhận không thấy dữ liệu A.
7. Tái hiện conflict hoặc lỗi mạng nếu flow đó là acceptance quan trọng.

E2E cần dữ liệu seed deterministic, cleanup và không phụ thuộc môi trường production.

## Tuần 4: CI và regression

### Buổi 7: quality gate

Pipeline tối thiểu:

1. Restore/install dependencies.
2. Format/lint nếu project có cấu hình.
3. Build backend/frontend.
4. Unit test.
5. Integration test với database test.
6. E2E critical flow nếu môi trường hỗ trợ.
7. Lưu test result/log/artifact khi fail.

Đặt timeout và retry có chủ đích. Không retry mù để che flaky test. Nếu test flaky, đánh dấu, tái hiện và sửa nguyên nhân.

### Buổi 8: regression từ bug thật

Mỗi bug quan trọng đi theo Prove-It Pattern:

1. Viết test tái hiện và xác nhận nó fail.
2. Sửa code tối thiểu.
3. Test pass.
4. Chạy full suite.
5. Ghi nguyên nhân và cách tránh lặp lại.

Ví dụ: stale search response, owner filter bị thiếu, migration làm mất dữ liệu, concurrency không trả 409 đều phải có regression test.

## Ma trận test của Sổ chi tiêu

| Boundary | Test chính | Bằng chứng |
|---|---|---|
| Parser/import | file rỗng, dòng lỗi, cancellation | unit |
| Report | tổng theo tháng/category, edge date | unit |
| API contract | status/body/header | integration |
| Database | migration, constraint, concurrency | integration |
| Authorization | A/B/anonymous/claim thiếu | integration |
| React UI | loading/form/filter/error | component |
| User journey | login → create → report | E2E |
| Deploy | health/config/rollback smoke test | deployment check |

## Dự án chặng: bộ kiểm thử đủ để sửa tự tin

1. Tập hợp unit tests từ Chặng 8–12.
2. Tạo integration fixture với database test cô lập.
3. Kiểm thử 401/403/404/409 và idempotency.
4. Thêm component tests cho state/error/accessibility.
5. Thêm một E2E critical flow.
6. Chạy pipeline trên pull request.
7. Tạo một bug cố ý cho owner filter hoặc stale response, quan sát test fail rồi sửa.
8. Ghi test strategy và known limitations trong README.

### Checkpoint

Cụ đạt chặng khi có thể:

- Nói test này chứng minh behavior nào và vì sao đặt ở tầng đó.
- Chạy test trên máy mới mà không dùng database cá nhân.
- Test bắt được lỗi sai quyền, conflict và response cũ.
- Đọc failure log, tái hiện được và không chỉ rerun đến khi xanh.
- Mỗi bug quan trọng có regression test.

## Interview checkpoint

1. Unit, integration và E2E khác nhau ở boundary nào?
2. Vì sao test pass nhưng production vẫn lỗi?
3. Khi nào dùng fake/stub/mock?
4. Vì sao mock mọi EF query có thể tạo false confidence?
5. Test authorization phải có case âm nào?
6. Vì sao test phụ thuộc thứ tự chạy là nguy hiểm?
7. Khi nào retry test là che flaky test?
8. Coverage cao nhưng chất lượng thấp có thể do đâu?
9. Một regression test tốt cần ghi lại điều gì?

Bài code-reading có thời gian 40 phút: suite có 100% pass nhưng test chỉ assert service được gọi. Cụ phải chỉ ra false confidence, thay một test bằng assertion trên response/state và đề xuất integration test còn thiếu.

## Tự chấm

- 0: có vài test nhưng không biết test boundary.
- 1: unit test chạy được, integration còn dùng database cá nhân.
- 2: có unit/integration/E2E critical, test quyền và regression.
- 3: thiết kế test strategy, CI gate và điều tra failure có hệ thống.
