# Chặng 9: Thiết kế code và design patterns vừa đủ

Thời lượng tham khảo: 3–4 tuần. Điều kiện vào: đã có importer hoặc report đơn giản ở Chặng 8.

Mục tiêu của chặng này không phải nhét thật nhiều pattern vào project. Cụ cần biết cách chia trách nhiệm, hướng phụ thuộc và mở rộng một behavior mà không kéo theo sửa dây chuyền. Pattern chỉ đáng dùng khi nó làm một thay đổi cụ thể dễ hơn.

## Mục tiêu đạt được

- Phân biệt inheritance với composition và chọn composition khi behavior cần thay đổi độc lập.
- Áp dụng SOLID qua tình huống thật, không học thuộc năm chữ cái.
- Đặt dependency direction: domain không biết HTTP/EF/UI; infrastructure thực hiện interface của application.
- Dùng Strategy, Factory và Adapter để mở rộng importer/report có kiểm soát.
- Tổ chức theo feature mà không biến project thành hàng chục abstraction rỗng.

## Tuần 1: trách nhiệm và hướng phụ thuộc

### Buổi 1: cohesion, coupling và composition

Một class có cohesion tốt khi các thành viên phục vụ cùng một trách nhiệm. Coupling cao khi class biết quá nhiều chi tiết của class khác. Trước khi tách class, ghi rõ behavior nào thay đổi cùng nhau.

So sánh hai cách:

- Controller vừa parse CSV, vừa tính tổng, vừa gọi EF: khó test và thay đổi.
- Controller nhận request, gọi use case; use case dùng importer/report interface; adapter cụ thể nằm ở infrastructure: mỗi phần có boundary rõ hơn.

Không tách IThingService chỉ vì muốn có interface. Interface nên bảo vệ một boundary hoặc cho phép thay thế dependency có lý do.

### Buổi 2: SOLID qua code Sổ chi tiêu

Dùng các câu hỏi sau để áp dụng SOLID:

- Single Responsibility: nếu format CSV đổi, có phải sửa class tính báo cáo không?
- Open/Closed: thêm báo cáo theo tuần có cần sửa mọi báo cáo cũ không?
- Liskov Substitution: implementation mới có giữ đúng hợp đồng không, hay trả null/lỗi khác hẳn?
- Interface Segregation: importer có bị bắt phải cài method export không dùng?
- Dependency Inversion: application đang phụ thuộc SQL Server cụ thể hay phụ thuộc abstraction?

Bài tập: lấy một service 100 dòng ở Chặng 5–8, đánh dấu các trách nhiệm, sau đó tách đúng một boundary. Viết test trước và sau refactor để chứng minh behavior không đổi.

### Buổi 3: feature folder và layered boundary

Có thể tổ chức phần API theo feature:

```text
Features/
  Expenses/
    CreateExpense/
    ListExpenses/
    ImportExpenses/
  Reports/
    ByCategory/
    ByMonth/
  Shared/
```

Hoặc dùng các layer Domain/Application/Infrastructure/Api. Cả hai đều là cách tổ chức; không có một cây thư mục tự động làm kiến trúc tốt. Với project học tập, chọn một cách và ghi dependency rule trong README.

Quy tắc tối thiểu:

- Domain không tham chiếu ASP.NET Core hoặc EF Core.
- Application chứa use case và interface cần thiết.
- Infrastructure chứa EF, file system, HTTP client và adapter.
- API chỉ xử lý transport, status code và authentication boundary.
- Frontend chỉ phụ thuộc contract HTTP, không phụ thuộc entity database.

## Tuần 2: Strategy, Factory và Adapter

### Buổi 4: Strategy cho báo cáo

Strategy phù hợp khi có nhiều thuật toán cùng một mục đích nhưng thay đổi độc lập.

```csharp
public interface IExpenseReport
{
    string Name { get; }
    ExpenseReport Calculate(IReadOnlyList<ExpenseResponse> items);
}

public sealed class MonthlyExpenseReport : IExpenseReport
{
    public string Name => "monthly";

    public ExpenseReport Calculate(IReadOnlyList<ExpenseResponse> items)
    {
        var total = items.Sum(x => x.Amount);
        return new ExpenseReport(Name, total, items.Count);
    }
}

public sealed record ExpenseReport(
    string Name,
    decimal Total,
    int ItemCount);
```

Thêm CategoryReport không nên yêu cầu sửa MonthlyExpenseReport. Tuy nhiên, nếu chỉ có một thuật toán và không có khả năng thay đổi, một function đơn giản dễ đọc hơn Strategy.

### Buổi 5: Factory và Adapter cho importer

Factory chọn implementation dựa trên format đã được whitelist. Adapter chuyển interface của thư viện/file reader về interface mà application hiểu.

```csharp
public interface IExpenseImporter
{
    IAsyncEnumerable<ExpenseImportRow> ReadAsync(
        Stream input,
        CancellationToken cancellationToken);
}

public sealed class ExpenseImporterFactory
{
    public IExpenseImporter Create(string format)
    {
        return format.ToLowerInvariant() switch
        {
            "csv" => new CsvExpenseImporter(),
            "json" => new JsonExpenseImporter(),
            _ => throw new ArgumentException("Unsupported format", nameof(format))
        };
    }
}
```

Factory không được dùng để che một danh sách dependency vô tận. Khi số implementation tăng, viết test cho mapping format → importer và trả lỗi rõ ràng cho format không hỗ trợ.

## Dự án chặng: thêm importer và report mà không phá phần cũ

1. Tạo application contract cho importer và report.
2. Di chuyển parser CSV sang adapter riêng.
3. Thêm JSON importer mà không sửa logic tính tổng.
4. Thêm report theo danh mục và theo tháng bằng Strategy.
5. Factory chỉ nhận format hợp lệ; không cho người dùng truyền tên type/class để reflection tùy ý.
6. Đăng ký dependency ở composition root, không gọi new infrastructure rải rác trong controller.
7. Viết một test contract dùng chung cho mọi importer: file hợp lệ, file rỗng, dòng lỗi và cancellation.
8. Ghi một sơ đồ dependency ngắn trong README.

### Điều kiện đạt

- Thêm JSON importer không cần sửa report.
- Thêm một report mới không cần sửa importer.
- Controller không còn biết chi tiết parse CSV/JSON.
- Có ít nhất một test chứng minh implementation mới tuân contract.
- Cụ giải thích được vì sao một abstraction được giữ lại và abstraction nào là thừa.

### Cảnh báo chống over-engineering

Chưa cần tạo mediator, CQRS, event bus hoặc generic repository chỉ để project trông “enterprise”. Nếu abstraction không giúp kiểm thử, thay thế dependency hoặc giới hạn phụ thuộc, hãy cân nhắc xóa nó.

## Interview checkpoint

1. Khi nào composition tốt hơn inheritance trong Sổ chi tiêu?
2. Vì sao một interface không tự động làm code dễ test hơn?
3. Strategy khác một if/else dài ở điểm nào?
4. Factory nên kiểm soát input format như thế nào?
5. Adapter giải quyết sự khác nhau giữa hai interface nào?
6. Dependency Inversion khác Dependency Injection ra sao?
7. Nếu thêm JSON mà phải sửa report, boundary nào đang sai?
8. Cụ sẽ bảo vệ domain khỏi EF Core bằng cách nào?

Bài code-reading có thời gian 30 phút: một controller mới new CsvParser(), new SqlConnection() và tính tổng ngay trong action. Hãy vẽ dependency, chỉ ra ba trách nhiệm và đề xuất một refactor nhỏ có test.

## Tự chấm

- 0: gọi tên được pattern nhưng chưa biết vấn đề nó giải quyết.
- 1: tách được interface nhưng chưa kiểm soát dependency.
- 2: thêm importer/report mới mà không sửa phần không liên quan.
- 3: giải thích trade-off giữa abstraction và sự đơn giản bằng ví dụ của project.
