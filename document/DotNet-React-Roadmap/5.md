# Chặng 5: HTTP và ASP.NET Core Web API

Thời lượng tham khảo: 4–5 tuần. Điều kiện vào: đã làm được schema/query ở Chặng 4 và biết class, async cơ bản chưa bắt buộc.

Mục tiêu là xây API cho Sổ chi tiêu: route rõ, validation, EF Core, lỗi có cấu trúc, logging, và authentication ở mức an toàn để học. Mỗi buổi chạy được một lát cắt nhỏ trước khi thêm tính năng.

## Hợp đồng dữ liệu dùng xuyên suốt Chặng 5–7

Từ phần này trở đi, backend và frontend dùng cùng một hợp đồng cho khoản chi. Database entity có navigation property `Category`, nhưng API không trả thẳng entity đó. API map entity sang DTO; React chỉ phụ thuộc vào DTO này.

```csharp
public sealed class CreateExpenseRequest
{
    public int CategoryId { get; set; }
    public decimal Amount { get; set; }
    public DateOnly SpentOn { get; set; }
    public string? Note { get; set; }
}

public sealed class ExpenseResponse
{
    public int Id { get; set; }
    public int CategoryId { get; set; }
    public string CategoryName { get; set; } = "";
    public decimal Amount { get; set; }
    public DateOnly SpentOn { get; set; }
    public string? Note { get; set; }
}
```

`GET /api/expenses` trả một mảng `ExpenseResponse`; `POST /api/expenses` nhận `CreateExpenseRequest` và trả khoản chi vừa tạo. Với cấu hình JSON mặc định của ASP.NET Core, tên property trong JSON là camelCase:

```json
{
  "id": 1,
  "categoryId": 2,
  "categoryName": "Ăn uống",
  "amount": 120000,
  "spentOn": "2026-09-02",
  "note": "Bữa trưa"
}
```

Vì vậy, frontend dùng `categoryId` để gửi dữ liệu và `categoryName` để hiển thị. Không dùng lẫn `category: string`, `Category: { ... }` và `CategoryName` cho cùng một response.

## Tuần 1: HTTP và endpoint đầu tiên

### Buổi 1: Request, response và status

HTTP request gồm method, URL, headers và có thể có body. Response gồm status, headers và body. GET đọc; POST tạo; PUT thường thay toàn bộ resource; PATCH cập nhật một phần khi API hỗ trợ; DELETE xóa. Đây là quy ước thiết kế, API cụ thể cần ghi rõ semantics.

Các status thường dùng:

- 200 OK cho đọc/sửa thành công có body.
- 201 Created khi tạo thành công, thường kèm Location.
- 204 No Content khi thành công không cần body.
- 400 khi request sai định dạng/quy tắc.
- 401 khi chưa xác thực; 403 khi đã xác thực nhưng không đủ quyền.
- 404 khi resource không tồn tại; 409 khi xung đột.
- 500 cho lỗi server chưa xử lý.

Bài tập: thiết kế GET /api/expenses, GET /api/expenses/5, POST /api/expenses, PUT /api/expenses/5, DELETE /api/expenses/5. Viết sample request/response và status trước khi code. Không đưa password vào URL.

### Buổi 2: Minimal API và Controller

Bắt đầu bằng một endpoint GET để thấy luồng:

```csharp
app.MapGet("/api/health", () =>
    Results.Ok(new { status = "ok" }));
```

Sau đó tạo ExpensesController khi dữ liệu cần route/action rõ hơn. Không có quy tắc mọi action phải trả đúng một chữ ký; có thể dùng ActionResult<T>, IResult hoặc IActionResult tùy phong cách. Với người mới, chọn một phong cách nhất quán.

Bài tập: tạo GET trả danh sách tạm trong memory, POST nhận DTO, và trả 201/400 phù hợp. Thử body thiếu category, amount âm và id không tồn tại.

### Buổi 3: Lát cắt database chạy được

Tạo ExpenseApiDbContext.cs và model tối thiểu. Lát cắt này giữ cùng quan hệ Category–Expense với Chặng 4, thay vì lưu tên category lặp lại trong mỗi expense:

```csharp
public sealed class ExpenseApiDbContext(DbContextOptions<ExpenseApiDbContext> options)
    : DbContext(options)
{
    public DbSet<Category> Categories => Set<Category>();
    public DbSet<Expense> Expenses => Set<Expense>();
}

public sealed class Category
{
    public int Id { get; set; }
    public string Name { get; set; } = "";
    public List<Expense> Expenses { get; set; } = new();
}

public sealed class Expense
{
    public int Id { get; set; }
    public int CategoryId { get; set; }
    public Category Category { get; set; } = null!;
    public decimal Amount { get; set; }
    public DateOnly SpentOn { get; set; }
    public string? Note { get; set; }
}
```

Trong `Program.cs`, đăng ký database, controllers và CORS. Chỉ gọi `builder.Build()` một lần:

```csharp
builder.Services.AddDbContext<ExpenseApiDbContext>(options =>
    options.UseSqlServer(
        builder.Configuration.GetConnectionString("ExpenseApiDb")));

builder.Services.AddControllers();
builder.Services.AddCors(options =>
{
    options.AddPolicy("frontend", policy =>
        policy.WithOrigins("http://localhost:5173")
              .AllowAnyHeader()
              .AllowAnyMethod());
});

var app = builder.Build();
app.UseCors("frontend");
app.MapControllers();
app.Run();
```

`http://localhost:5173` là origin dev thường dùng của Vite. Nếu frontend chạy ở origin khác, ghi đúng origin đó trong `WithOrigins`; không dùng `AllowAnyOrigin` chỉ để né lỗi. API controller phải kế thừa `ControllerBase`, có `[ApiController]` và route rõ ràng.

Thêm using `Microsoft.EntityFrameworkCore` và tạo migration đầu tiên:

```text
dotnet ef migrations add InitialCreate
dotnet ef database update
```

Tạo `Controllers/ExpensesController.cs` để GET/POST dùng đúng DTO ở phần hợp đồng:

```csharp
using Microsoft.AspNetCore.Mvc;
using Microsoft.EntityFrameworkCore;

[ApiController]
[Route("api/expenses")]
public sealed class ExpensesController(ExpenseApiDbContext db) : ControllerBase
{
    [HttpGet]
    public async Task<ActionResult<IReadOnlyList<ExpenseResponse>>> GetAll(
        CancellationToken cancellationToken)
    {
        var items = await db.Expenses
            .AsNoTracking()
            .OrderByDescending(x => x.SpentOn)
            .ThenByDescending(x => x.Id)
            .Select(x => new ExpenseResponse
            {
                Id = x.Id,
                CategoryId = x.CategoryId,
                CategoryName = x.Category.Name,
                Amount = x.Amount,
                SpentOn = x.SpentOn,
                Note = x.Note
            })
            .ToListAsync(cancellationToken);

        return Ok(items);
    }

    [HttpGet("{id:int}")]
    public async Task<ActionResult<ExpenseResponse>> GetById(
        int id, CancellationToken cancellationToken)
    {
        var item = await db.Expenses
            .AsNoTracking()
            .Where(x => x.Id == id)
            .Select(x => new ExpenseResponse
            {
                Id = x.Id,
                CategoryId = x.CategoryId,
                CategoryName = x.Category.Name,
                Amount = x.Amount,
                SpentOn = x.SpentOn,
                Note = x.Note
            })
            .SingleOrDefaultAsync(cancellationToken);

        if (item is null) return NotFound();
        return Ok(item);
    }

    [HttpPost]
    public async Task<ActionResult<ExpenseResponse>> Create(
        CreateExpenseRequest request,
        CancellationToken cancellationToken)
    {
        if (request.CategoryId <= 0)
        {
            return BadRequest(new ValidationProblemDetails(new Dictionary<string, string[]>
            {
                ["categoryId"] = new[] { "CategoryId must be greater than 0." }
            }));
        }

        if (request.Amount < 0)
        {
            return BadRequest(new ValidationProblemDetails(new Dictionary<string, string[]>
            {
                ["amount"] = new[] { "Amount must be greater than or equal to 0." }
            }));
        }

        if (request.SpentOn == default)
        {
            return BadRequest(new ValidationProblemDetails(new Dictionary<string, string[]>
            {
                ["spentOn"] = new[] { "SpentOn is required." }
            }));
        }

        var categoryExists = await db.Categories
            .AnyAsync(x => x.Id == request.CategoryId, cancellationToken);

        if (!categoryExists)
        {
            return BadRequest(new ValidationProblemDetails(new Dictionary<string, string[]>
            {
                ["categoryId"] = new[] { "Category does not exist." }
            }));
        }

        var expense = new Expense
        {
            CategoryId = request.CategoryId,
            Amount = request.Amount,
            SpentOn = request.SpentOn,
            Note = request.Note
        };

        db.Expenses.Add(expense);
        await db.SaveChangesAsync(cancellationToken);

        var response = await db.Expenses
            .AsNoTracking()
            .Where(x => x.Id == expense.Id)
            .Select(x => new ExpenseResponse
            {
                Id = x.Id,
                CategoryId = x.CategoryId,
                CategoryName = x.Category.Name,
                Amount = x.Amount,
                SpentOn = x.SpentOn,
                Note = x.Note
            })
            .SingleAsync(cancellationToken);

        return CreatedAtAction(nameof(GetById), new { id = expense.Id }, response);
    }
}
```

Kết quả mong đợi: database `ExpenseApiDb` được tạo, bảng `Expenses` xuất hiện; `GET /api/expenses` trả mảng DTO (hoặc `[]` khi chưa có dữ liệu), `GET /api/expenses/1` trả 200/404, và `POST /api/expenses` trả 201 khi hợp lệ hoặc 400 khi validation thất bại. `[ApiController]` cũng giúp biến lỗi binding như ngày không hợp lệ thành response 400. Nếu lệnh migration đụng bảng cũ, kiểm tra đúng connection string/database name trước khi xóa hay sửa migration.

## Tuần 2: DI, EF Core và database

### Buổi 4: Dependency injection và lifetime

DI cung cấp dependency qua constructor thay vì class tự new mọi thứ. Transient tạo instance mỗi lần yêu cầu; Scoped thường một instance trong một request; Singleton sống suốt process. DbContext được đăng ký scoped theo cấu hình mặc định của AddDbContext, nhưng đây là mặc định có thể thay đổi, không phải luật “mọi DbContext luôn scoped”. Singleton không an toàn cho DbContext và state theo user.

```csharp
builder.Services.AddScoped<IExpenseService, ExpenseService>();
```

Bài tập: đăng ký service, inject vào controller, và đặt breakpoint để xem cùng request dùng instance nào. Không lưu List dữ liệu người dùng vào singleton.

### Buổi 5: EF Core model và migration tiếp theo

`InitialCreate` đã được tạo ở Buổi 3. Không chạy lại đúng tên migration đó. EF Core migration dùng để ghi nhận thay đổi model theo từng bước; mỗi thay đổi mới phải có tên migration mới.

Để có một thay đổi model cụ thể, thêm trường tùy chọn chỉ dùng nội bộ cho việc theo dõi thời điểm tạo:

```csharp
public DateTime? CreatedAtUtc { get; set; }
```

Đặt property này trong `Expense`. Sau đó cập nhật object tạo expense trong controller:

```csharp
var expense = new Expense
{
    CategoryId = request.CategoryId,
    Amount = request.Amount,
    SpentOn = request.SpentOn,
    Note = request.Note,
    CreatedAtUtc = DateTime.UtcNow
};
```

Chạy:

```text
dotnet ef migrations add AddExpenseCreatedAtUtc
dotnet ef database update
```

Nếu lệnh báo migration đã tồn tại, không đổi tên tùy tiện để chạy tiếp; hãy xem `dotnet ef migrations list`, kiểm tra thư mục `Migrations` và database đang dùng đúng `ExpenseApiDb` chưa. Bài tập: thêm migration mới, đọc file migration xem cột nào được thêm, rồi kiểm tra bảng bằng SQL Server Object Explorer/SSMS.

### Buổi 6: Query, projection và N+1

EF Core dịch LINQ thành SQL khi query thực thi. Chỉ lấy cột cần trả bằng Select; dùng AsNoTracking cho đọc-only khi không cần theo dõi thay đổi. N+1 xảy ra khi code tạo một query lấy danh sách rồi thực hiện thêm query cho từng dòng, thường do lazy loading hoặc query trong loop. Chỉ truy cập navigation property không tự động có nghĩa N+1 nếu navigation đã được Include/projection hoặc dữ liệu đã tải.

```csharp
// Đây là đoạn trích trong endpoint/service; from và to thường đến từ query parameters.
DateOnly from = new(2026, 9, 1);
DateOnly to = new(2026, 10, 1);

var rows = await db.Expenses
    .AsNoTracking()
    .Where(x => x.SpentOn >= from && x.SpentOn < to)
    .Select(x => new
    {
        x.Id,
        CategoryName = x.Category.Name,
        x.Amount,
        x.SpentOn
    })
    .ToListAsync();
```

Đoạn projection trên chỉ lấy các cột cần hiển thị và là ví dụ minh họa, không phải toàn bộ endpoint. Include có thể tạo một query hoặc nhiều query tùy provider/configuration; đừng hứa “luôn đúng một SQL”. Bật logging ở môi trường học để xem câu SQL. Không cần tạo 50.000 dòng hoặc tối ưu trước khi đo; bắt đầu bằng 10–20 dòng và quan sát.

## Tuần 3: validation, lỗi và async

### Buổi 7: DTO và validation

Không nhận entity database trực tiếp làm contract nếu API cần kiểm soát field. Tạo CreateExpenseRequest và ExpenseResponse. Kiểm tra category rỗng, amount không âm, date hợp lệ; trả validation errors rõ ràng.

Bài tập: POST hợp lệ trả 201; body lỗi trả 400; id category không có trả 400 hoặc 404 theo quy ước bạn ghi trong README. Viết test cho từng case.

### Buổi 8: Async và ProblemDetails

await giúp không chặn thread trong lúc chờ I/O; không biến code thành nhanh tự động. Tránh .Result/.Wait vì chúng có thể block thread và trong một số môi trường gây deadlock hoặc starvation; không khẳng định luôn luôn deadlock. Dùng async Task cho API; async void chỉ phù hợp event handler đặc biệt.

ASP.NET Core có middleware xử lý exception và ProblemDetails. Ở môi trường production không trả stack trace hay secret cho client; ghi log server với correlation id.

```csharp
builder.Services.AddProblemDetails();
var app = builder.Build();
app.UseExceptionHandler();
```

Bài tập: cố tình ném exception trong service, kiểm tra response không lộ stack trace, đọc log để tìm nguyên nhân. Thêm status 404 khi id không tồn tại.

### Buổi 9: logging và kiểm thử API

Dùng ILogger có level và thông tin có thể tìm kiếm; không log password, token, connection string hay body nhạy cảm. Test API bằng file .http, curl hoặc Postman. Ghi expected status và response cho POST, GET, lỗi validation, 404.

## Tuần 4–5: authentication và dự án

### Buổi 10: Authentication/authorization

Authentication trả lời “ai đang gọi”; authorization trả lời “họ được phép làm gì”. JWT thường được ký để kiểm tra toàn vẹn và nguồn phát hành; payload được base64url nên không nên chứa secret, và JWT không mặc nhiên là dữ liệu được mã hóa. Secret signing key phải được quản lý ngoài source.

ASP.NET Core Identity cung cấp user/password, token và policy theo cấu hình; Identity API endpoints built-in token không đồng nghĩa với việc bạn đã có JWT. Đọc rõ loại token và flow trước khi viết frontend. Với dự án học, có thể dùng cookie/Identity API cùng frontend proxy; nếu dùng bearer JWT, chỉ làm khi đã hiểu expiry, storage, HTTPS, CSRF/XSS trade-off.

Bài tập: thêm user demo, bảo vệ GET/POST expenses bằng policy, test 401 khi thiếu credential và 403 khi thiếu quyền. Không log password hoặc token.

### Buổi 11: Dự án chặng

API cần có GET danh sách với phân trang/lọc ngày, POST, PUT, DELETE, validation, ProblemDetails, logging, migration, và test cho luồng chính. Thêm auth sau khi CRUD chạy ổn; không để auth che khuất lỗi database.

Checkpoint: mở Network hoặc file .http, bạn giải thích được request đi qua middleware, endpoint/service, EF Core và database rồi response quay về.
