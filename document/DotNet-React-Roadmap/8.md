# Chặng 8: C# chuyên sâu và lập trình bất đồng bộ

Thời lượng tham khảo: 3–4 tuần. Điều kiện vào: đã hoàn thành Chặng 7 và có thể giải thích luồng click → React state → API → database của Sổ chi tiêu.

Chặng này không nhằm học thuộc mọi tính năng của C#. Mục tiêu là hiểu code đang chạy ở đâu, dữ liệu được sở hữu bởi ai, tài nguyên được giải phóng thế nào và một thao tác bất đồng bộ dừng ra sao.

## Mục tiêu đạt được

- Phân biệt value type/reference type trong tình huống thực tế; hiểu equality của class, record và collection.
- Viết generic, delegate/lambda và LINQ mà không nhầm giữa việc xây query với việc thực thi query.
- Dùng nullable, exception và Result/validation một cách có chủ đích.
- Quản lý stream/file bằng using hoặc await using.
- Viết tác vụ async có cancellation; giải thích được async không mặc định tạo thread mới.
- Nhận diện state dùng chung và chọn cách bảo vệ nó thay vì thêm lock theo cảm tính.

## Tuần 1: dữ liệu, kiểu và hàm

### Buổi 1: value type, reference type và equality

int, decimal, DateOnly, struct thường mang giá trị trực tiếp; class và array là object được tham chiếu. Đây là mô hình hữu ích để giải thích việc gán biến, truyền tham số và thay đổi object, nhưng không nên biến nó thành khẩu hiệu “value luôn nằm trên stack, reference luôn nằm trên heap”. Vị trí lưu trữ còn phụ thuộc vào runtime và cách biến được dùng.

```csharp
public sealed record ExpenseKey(int CategoryId, DateOnly SpentOn);

var first = new ExpenseKey(2, new DateOnly(2026, 9, 22));
var second = new ExpenseKey(2, new DateOnly(2026, 9, 22));

Console.WriteLine(first == second); // record so sánh theo giá trị
```

So sánh record theo giá trị không có nghĩa mọi class đều như vậy. Với entity EF Core, nên hiểu rõ identity của entity và cách Equals/GetHashCode ảnh hưởng tới collection. Bài tập: tạo hai object Expense có cùng field, thử Equals, rồi viết lý do vì sao entity không nên tùy tiện chuyển thành record.

### Buổi 2: generic, delegate và lambda

Generic giúp viết logic dùng được cho nhiều kiểu mà vẫn giữ kiểm tra kiểu lúc compile. Delegate là một kiểu đại diện cho hàm; lambda là cách viết ngắn để tạo function value.

```csharp
static IEnumerable<T> WhereNotNull<T>(IEnumerable<T?> source)
    where T : class
{
    foreach (var item in source)
    {
        if (item is not null) yield return item;
    }
}

Func<ExpenseResponse, bool> isLarge = item => item.Amount >= 1_000_000m;
var largeItems = items.Where(isLarge);
```

Bài tập: viết Map đơn giản nhận IEnumerable<TSource> và Func<TSource, TResult>, sau đó so sánh với LINQ Select. Không viết lại cả thư viện LINQ; mục tiêu là hiểu generic và delegate.

## Tuần 2: LINQ, nullable và lỗi

### Buổi 3: deferred execution

Các toán tử LINQ như Where/Select thường chỉ xây pipeline. Query có thể chạy khi foreach, ToList, Count hoặc toán tử terminal khác được gọi.

```csharp
var query = expenses
    .Where(x => x.Amount > 0)
    .Select(x => x.Amount);

expenses.Add(new Expense { Amount = 50_000m });

var values = query.ToList(); // pipeline đọc dữ liệu ở thời điểm này
```

Nếu cần snapshot, gọi ToList ở ranh giới rõ ràng. Không gọi ToList vô thức sau mỗi bước vì sẽ tạo thêm bộ nhớ và có thể làm query database chạy sớm. Với EF Core, luôn phân biệt LINQ được dịch thành SQL với LINQ chạy trong memory; kiểm tra bằng log SQL hoặc ToQueryString ở môi trường học.

Bài tập: cho một danh sách expense, ghi lại thời điểm query được thực thi. Sau đó đổi nguồn thành IQueryable EF Core và chỉ ra đoạn nào còn được dịch sang SQL.

### Buổi 4: nullable và exception boundary

Nullable reference types là cảnh báo ở compile time; chúng không tự kiểm tra JSON hoặc dữ liệu người dùng lúc chạy. Dữ liệu từ API/file/database vẫn cần validation runtime.

Quy ước trong project:

- Lỗi nhập liệu dự kiến trả về validation result hoặc 400 ở boundary API.
- Resource không tồn tại trả 404.
- Lỗi hệ thống cần được log và chuyển thành response an toàn; không nuốt exception bằng catch rỗng.
- Không dùng exception làm flow bình thường cho mọi điều kiện có thể kiểm tra trước.

Bài tập: viết parser ngày tháng trả bool TryParse cho input người dùng; viết một hàm khác ném exception cho lỗi invariant không thể tiếp tục. Ghi rõ caller nào chịu trách nhiệm xử lý.

## Tuần 3: tài nguyên, async và cancellation

### Buổi 5: IDisposable và stream

File stream, database connection, response stream và một số resource khác cần được giải phóng. using bảo đảm Dispose được gọi khi rời khỏi scope; await using dùng cho resource có DisposeAsync.

```csharp
await using var stream = File.OpenRead(path);
using var reader = new StreamReader(stream);

while (await reader.ReadLineAsync(cancellationToken) is { } line)
{
    // parse một dòng, không nạp cả file vào bộ nhớ
}
```

Bài tập: đọc một file CSV nhỏ trước, sau đó thử file lớn. So sánh ReadAllLines với đọc streaming; ghi lại trade-off bộ nhớ và độ đơn giản.

### Buổi 6: async, cancellation và thread safety

async/await mô tả cách tiếp tục một công việc khi I/O hoàn tất; nó không đồng nghĩa với việc tạo một thread mới. Cancellation là tín hiệu hợp tác: caller yêu cầu dừng, còn callee phải truyền token xuống và kiểm tra tại các điểm phù hợp.

```csharp
public static async Task<int> CountImportedRowsAsync(
    string path,
    CancellationToken cancellationToken)
{
    var count = 0;

    await using var stream = File.OpenRead(path);
    using var reader = new StreamReader(stream);

    while (await reader.ReadLineAsync(cancellationToken) is not null)
    {
        cancellationToken.ThrowIfCancellationRequested();
        count++;
    }

    return count;
}
```

Không dùng .Result/.Wait() để “đợi cho xong” trong web request. Không chia sẻ DbContext giữa các thread. Với counter dùng chung, chọn thiết kế không chia sẻ state, channel/queue hoặc primitive phù hợp; lock chỉ giải quyết một nhóm vấn đề nhỏ và không thể dùng quanh await.

Bài tập: thêm nút Hủy import vào frontend. API nhận CancellationToken; service dừng đọc file. Khi server trả `cancelled`, UI hiển thị hủy đã được server xác nhận; khi browser abort, lỗi mạng hoặc phản hồi không đọc được, UI giữ `unconfirmed` và yêu cầu đối chiếu rõ ràng thay vì báo đã hủy.

## Dự án chặng: import chi tiêu có thể hủy

### Lát cắt tham chiếu có thể chạy

Phần thực hành tích hợp nối ba reference: [async/parser Stage 8](reference/stage-08-async/README.md), [persistence Stage 8](reference/stage-08-persistence/README.md), [API Stage 8](reference/stage-08-integration/api/README.md) và [frontend Stage 8](reference/stage-08-integration/frontend/README.md). Đây là fixture LocalDB học tập tách biệt; mỗi lần chạy phải dùng thư mục evidence và tên database mới theo hướng dẫn trong README, giữ log/TRX, không ghi vào fixture cũ và không dùng dữ liệu Visualization hay learner cũ. Chặng 7 phải hoàn tất trước; các bài authentication/ownership ở Chặng 11 và test API hệ thống hóa ở Chặng 13 vẫn là điều kiện sau đó.

Thứ tự chạy: đọc parser và persistence trước, chạy build/test API với evidence mới, khởi động Kestrel strict `http://127.0.0.1:0` bằng `DN54_DB_NAME` mới, kiểm tra POST/GET thủ công nếu môi trường cho phép, rồi chạy frontend với `VITE_API_ORIGIN=http://127.0.0.1:<cổng API đã in>`. Browser gọi URL tương đối `/api`; biến này chỉ cấu hình Vite local proxy. Thiếu biến khi `npm run dev` phải dừng với lỗi cấu hình rõ ràng; production build không cần gọi API. Nếu không có LocalDB, browser hoặc transport thật, ghi blocker và để observation incomplete.

Contract cần giữ khi đọc code:

- Parser nhận stream CSV và `CancellationToken`; endpoint không cho client chọn database, user hoặc fault hook. Hook fault/cancellation là seam DI chỉ dành cho test/instructor, không phải HTTP selector.
- Import validation là atomic: một file hợp lệ được commit cùng transaction; duplicate chỉ trong cùng file được skip. Lỗi validation hoặc request bị `rejected` không ghi expense, nhưng `readRows` và `skippedDuplicates` có thể lớn hơn 0; `acceptedRows` phải bằng 0. File rỗng/header-only là committed no-op với ba count bằng 0.
- `amount` là chuỗi tiền exact hai chữ số, tối đa `9999999999999999.99`; browser không dùng `Number`/`parseFloat`. Response lỗi dùng mã an toàn, không hiển thị exception/path server.
- `cancelled` chỉ có nghĩa server đã quan sát cancellation trước commit và trả 499; đó là trạng thái được server xác nhận. Browser abort, lỗi mạng hoặc phản hồi không đọc được chỉ là `unconfirmed` cho đến khi người học đối chiếu rõ ràng. GET chỉ hiển thị dữ liệu đối chiếu và không thể quy kết một GET cho request POST cụ thể; không tự retry POST.

Xây vertical slice mới từ file đến database:

1. Tạo ExpenseImportRow chỉ chứa dữ liệu đầu vào và không nhận entity EF trực tiếp.
2. Tạo IExpenseImporter trả IAsyncEnumerable<ExpenseImportRow>.
3. Viết importer CSV; JSON có thể là bước mở rộng sau khi CSV chạy ổn.
4. Validate từng dòng: categoryId, amount, ngày, note và dòng trùng.
5. Nhận CancellationToken từ endpoint đến stream reader.
6. Chỉ ghi database sau khi có chiến lược rõ: ghi theo batch hoặc đọc trước rồi xác nhận; không để một file lỗi một nửa mà người học không biết trạng thái.
7. Trả báo cáo gồm số dòng đọc, số dòng hợp lệ, số dòng bỏ qua và lỗi theo dòng.

### Dữ liệu biên bắt buộc

- File rỗng, file chỉ có header, dòng thiếu cột.
- Amount âm, decimal dùng dấu phẩy/chấm không đúng culture.
- Ngày không hợp lệ, category không tồn tại, dòng trùng.
- Hủy trước khi đọc, hủy giữa file và hủy sau khi đã ghi một batch.
- File rất lớn hơn bộ nhớ dự kiến.

## Interview checkpoint

Tự trả lời bằng lời, sau đó viết một ví dụ ngắn:

1. async có tạo thread mới không? I/O-bound và CPU-bound khác nhau thế nào?
2. Vì sao IQueryable không nên bị chuyển sang IEnumerable quá sớm?
3. Vì sao gọi ToList làm thay đổi thời điểm chạy của LINQ?
4. CancellationToken có tự dừng một method không?
5. using và garbage collector giải quyết hai vấn đề nào khác nhau?
6. Vì sao không dùng một DbContext đồng thời trên nhiều thread?
7. record so sánh theo giá trị có phù hợp cho mọi EF entity không?
8. Đọc đoạn import bị lỗi: cụ sẽ đặt log và test ở những boundary nào?

Bài debug có thời gian 25 phút: một import đọc được 10.000 dòng nhưng bấm Hủy vẫn tiếp tục ghi dữ liệu. Cụ phải tái hiện, giải thích token bị mất ở đâu và viết regression test trước khi sửa.
