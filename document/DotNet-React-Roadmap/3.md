# Chặng 3: C# cho ứng dụng nhỏ

Thời lượng tham khảo: 3–4 tuần. Điều kiện vào: hoàn thành Chặng 1 và biết phân rã, collection, debug ở Chặng 2.

Bạn sẽ chuyển app chi tiêu từ nhiều biến rời sang mô hình có dữ liệu, quy tắc và nơi lưu trữ rõ ràng. Chỉ học đủ OOP để giải quyết app; SOLID là nguyên tắc gợi ý, không phải danh sách phải thuộc.

## Tuần 1: Class, object và đóng gói

### Buổi 1: Class và object

Class mô tả dữ liệu/hành vi; object là một đối tượng cụ thể được tạo từ class. Constructor là phần có cùng tên class, chạy khi dùng `new` để tạo object. `public` cho phép mã bên ngoài truy cập; `private` giới hạn trong class. Ví dụ dùng `sealed` để không cho class khác kế thừa, chưa cần học kế thừa ở bài này. `{ get; }` cho phép đọc property; trong ví dụ này giá trị được gán trong constructor.

```csharp
public sealed class Expense
{
    public Expense(string category, decimal amount)
    {
        if (string.IsNullOrWhiteSpace(category))
            throw new ArgumentException("Danh mục không được rỗng.", nameof(category));
        if (amount < 0)
            throw new ArgumentOutOfRangeException(nameof(amount));

        Category = category.Trim();
        Amount = amount;
    }

    public string Category { get; }
    public decimal Amount { get; }
}

```

Tạo class ở Expense.cs, rồi gọi nó từ Program.cs:

```csharp
var expense = new Expense("Điện", 500_000m);
Console.WriteLine(expense.Category + ": " + expense.Amount);
```

Expense.cs nằm cùng thư mục với Program.cs. Chạy `dotnet run` từ thư mục ExpenseConsole; kết quả là `Điện: 500000`. `new Expense(...)` tạo đối tượng, dấu chấm đọc property. `nameof(amount)` lấy tên tham số để báo lỗi; `throw` phát tín hiệu lỗi, học cách bắt ở Buổi 4. Thử thêm một đối tượng khác và kiểm tra hai khoản có giá trị độc lập.

Bài tập: thêm DateOnly Date và một id kiểu int hoặc Guid theo cách bạn hiểu. Quy định rõ date nào hợp lệ và viết ba test thủ công: hợp lệ, category rỗng, amount âm.

### Buổi 2: Đóng gói đúng nghĩa

Property public get/set không tự động tạo ra invariant; nếu mọi nơi đều được set tùy ý, object vẫn có thể sai. Có thể dùng private set, constructor, method và validation để kiểm soát thay đổi.

```csharp
public sealed class Budget
{
    public Budget(decimal limit)
    {
        if (limit < 0) throw new ArgumentOutOfRangeException(nameof(limit));
        Limit = limit;
    }

    public decimal Limit { get; private set; }

    public void ChangeLimit(decimal newLimit)
    {
        if (newLimit < 0) throw new ArgumentOutOfRangeException(nameof(newLimit));
        Limit = newLimit;
    }
}
```

Bài tập: thêm method UpdateAmount cho Expense hoặc tạo ExpenseService. Nêu invariant bằng câu tiếng Việt trước khi code. Không cần kế thừa chỉ để chứng minh OOP.

### Buổi 3: Interface, composition và SRP

Interface là hợp đồng hành vi; class implement phải đáp ứng hợp đồng. Composition là ghép các object nhỏ, thường dễ thay đổi hơn kế thừa sâu. Single Responsibility nói về một lý do thay đổi, không phải “class chỉ có đúng một method”.

Ví dụ tối thiểu:

```csharp
public interface IExpenseStore
{
    List<Expense> Load();
    void Save(List<Expense> items);
}

public sealed class MemoryExpenseStore : IExpenseStore
{
    private readonly List<Expense> items = new();

    public List<Expense> Load() => new(items);
    public void Save(List<Expense> newItems)
    {
        items.Clear();
        items.AddRange(newItems);
    }
}
```

Service có thể nhận IExpenseStore trong constructor và gọi Load/Save mà không biết dữ liệu nằm ở bộ nhớ hay file. Bài tập: thay MemoryExpenseStore bằng một FileExpenseStore sau khi đã hiểu bản hợp đồng.

Đặt interface và class vào các file cùng tên, cùng thư mục dự án. `: IExpenseStore` nghĩa là class thực hiện hợp đồng. `readonly` ngăn gán lại biến items sau khi khởi tạo, không cấm thay đổi danh sách bên trong. `new(items)` là cách viết ngắn của `new List<Expense>(items)`, tạo bản sao danh sách; các đối tượng phần tử vẫn được chia sẻ. `=>` ở Load là cách viết ngắn cho thân hàm trả về một biểu thức. Trong Program.cs, thử gọi:

```csharp
IExpenseStore store = new MemoryExpenseStore();
store.Save(new List<Expense> { new Expense("Điện", 100m) });
Console.WriteLine(store.Load().Count); // 1
```

Bài tập: tách ba trách nhiệm trong app:

- ExpenseService kiểm tra và áp dụng quy tắc.
- ExpenseFileStore đọc/ghi dữ liệu.
- ConsoleUi nhận input và in output.

Ban đầu dùng interface tối thiểu IExpenseStore để service không phụ thuộc trực tiếp file. Không cần Clean Architecture nhiều tầng.

### Buổi 4: Exception và kết quả lỗi

Dùng exception cho điều kiện bất thường hoặc lỗi không thể xử lý tại chỗ; lỗi người dùng nhập sai thường nên được kiểm tra và trả về thông báo ngay. finally chạy khi rời khỏi try/catch theo luật điều khiển thông thường, nhưng không có nghĩa là “mọi process chắc chắn sẽ tiếp tục” nếu bị kill đột ngột.

```csharp
try
{
    string json = File.ReadAllText("expenses.json");
    Console.WriteLine(json.Length);
}
catch (FileNotFoundException)
{
    Console.WriteLine("Chưa có file dữ liệu, dùng danh sách rỗng.");
}
catch (IOException error)
{
    Console.WriteLine("Không đọc được file: " + error.Message);
}
```

Bài tập: bắt lỗi khi đọc file hỏng, đưa ra thông báo và giữ lại danh sách hiện tại. Không dùng catch trống. Tạo test cho file không tồn tại và JSON sai.

## Tuần 2: File, JSON và Git

### Buổi 5: Đường dẫn và disposal

File API làm việc với path; dùng Path.Combine thay vì nối chuỗi dấu gạch. Stream/StreamReader implements IDisposable; using bảo đảm Dispose được gọi khi rời block bình thường.

```csharp
string path = Path.Combine("data", "expenses.txt");
Directory.CreateDirectory(Path.GetDirectoryName(path)!);
File.WriteAllText(path, "demo");
string text = File.ReadAllText(path);
Console.WriteLine(text);
```

Bài tập: lưu mỗi khoản thành một dòng theo định dạng bạn tự quy định. Thử thư mục chưa có, file rỗng và ký tự newline trong category. Khi in “đã đóng file”, đó chỉ là thông báo của bạn; hãy hiểu disposal đến từ using hoặc API high-level.

### Buổi 6: JSON

JSON phù hợp lưu object có cấu trúc. System.Text.Json serialize object thành text và deserialize ngược lại; input ngoài hệ thống vẫn cần validation sau deserialize.

```csharp
using System.Text.Json;

var items = new List<Expense>
{
    new Expense("Điện", 500_000m)
};

string json = JsonSerializer.Serialize(items, new JsonSerializerOptions
{
    WriteIndented = true
});
File.WriteAllText("expenses.json", json);

string savedJson = File.ReadAllText("expenses.json");
var loaded = JsonSerializer.Deserialize<List<Expense>>(savedJson);
Console.WriteLine(loaded?.Count ?? 0);
```

Khối trên dùng Expense gốc ở Buổi 1, có constructor công khai với tên tham số khớp property, nên System.Text.Json có thể khôi phục nó. Kết quả là 1. Nếu bạn đã mở rộng Expense, hãy thử ví dụ trong một dự án luyện riêng dùng đúng class gốc trước. `loaded?.Count` chỉ đọc Count khi loaded khác null; `?? 0` dùng 0 nếu kết quả bên trái null. `using System.Text.Json;` ở đầu file đưa tên kiểu trong namespace đó vào phạm vi sử dụng; khác với `using` dùng để dọn tài nguyên.

Bài tập mở rộng: lưu thêm id và ngày chi rồi đọc lại. DTO là class đơn giản dùng để chuyển dữ liệu giữa các phần; chỉ thêm DTO khi hình dạng dữ liệu lưu file khác với class nghiệp vụ. Khi JSON sai, bắt JsonException và giữ nguyên file hỏng để kiểm tra, không âm thầm ghi đè bằng danh sách rỗng. Ví dụ ghi file trên dùng dữ liệu luyện tập; không chạy lên file dữ liệu thật cần giữ.

### Buổi 7: Git tối thiểu

Git là lịch sử thay đổi, không phải nơi tự động hiểu code. Làm một commit sau khi app chạy, một commit sau khi thêm JSON, và một commit sau khi sửa lỗi. Mỗi commit nên có câu mô tả có ích.

```text
dotnet new gitignore
git init
git add .
git commit -m "Create console expense app"
```

Chạy trong thư mục ExpenseConsole. Trước `git add .`, thêm `data/` và `expenses.json` vào .gitignore nếu đó là dữ liệu cá nhân. Nếu Git yêu cầu danh tính, cấu hình `git config user.name "Tên của bạn"` và `git config user.email "Email bạn chọn"` trong dự án rồi commit lại; đây là thông tin tác giả commit, không phải đăng nhập. Kiểm tra file sắp lưu bằng `git status` và thay đổi bằng `git diff`.

Bài tập: tạo nhánh thử nghiệm, sửa menu, xem diff rồi quay lại bằng thao tác Git an toàn. Không chạy reset --hard lên thư mục có dữ liệu chưa lưu.

## Tuần 3: test và refactor app

### Buổi 8: Unit test

Unit test kiểm tra một đơn vị logic với dependency kiểm soát được. Integration test kiểm tra nhiều phần cùng chạy, ví dụ service + file hoặc API + database. Không có quy tắc cấm test chạm database; chỉ cần biết nó là loại test khác, chậm hơn và cần dữ liệu cô lập.

Từ terminal đang ở ExpenseConsole, đi lên thư mục cha để tạo test project cạnh nó. Không tạo test project bên trong thư mục console vì C# có thể tự gom cả file test vào app:

```text
cd ..
dotnet new xunit -o ExpenseConsole.Tests
dotnet add ExpenseConsole.Tests reference ExpenseConsole
dotnet test ExpenseConsole.Tests
```

Mở ExpenseConsole.Tests/UnitTest1.cs, thay nội dung bằng ví dụ này. Template xUnit có sẵn global using cho Xunit; nếu editor báo không biết Fact hoặc Assert, thêm `using Xunit;` ở đầu file. Expense phải là public như Buổi 1.

```csharp
public class ExpenseTests
{
    [Fact]
    public void Constructor_RejectsNegativeAmount()
    {
        Assert.Throws<ArgumentOutOfRangeException>(
            () => new Expense("Điện", -1m));
    }
}
```

`[Fact]` đánh dấu method là một test; Assert.Throws yêu cầu đoạn gọi bên trong phải ném đúng loại lỗi. `() => ...` là một hàm không tham số để framework gọi trong lúc kiểm tra, không phải gọi ngay khi khai báo. Chạy lại `dotnet test ExpenseConsole.Tests` từ thư mục cha: cần thấy Passed và 0 Failed. Đổi -1m thành 1m sẽ làm test thất bại vì constructor không còn ném lỗi; quan sát rồi đổi lại. Đó là cách kiểm tra test thực sự phát hiện điều kiện bạn muốn.

Tên test nói rõ điều kiện và kết quả. Bài tập: viết thêm test [Fact] cho category rỗng, số tiền bằng 0, tổng danh sách rỗng, và lọc theo danh mục. Chạy dotnet test sau mỗi nhóm thay đổi.

Tạo test cho:

- Expense từ chối category rỗng và amount âm.
- ExpenseService tính tổng đúng với danh sách rỗng và danh sách có số 0.
- lọc theo danh mục không phân biệt hoa thường nếu đó là quy tắc bạn chọn.

Không test Console bằng cách so sánh cả màn hình ở bước này. Hãy tách logic khỏi UI để test dễ.

### Buổi 9: Refactor có kiểm soát

Di chuyển từng trách nhiệm một, chạy lại app sau mỗi thay đổi. Nếu đổi cấu trúc file và logic cùng lúc, lỗi khó định vị. Tên class/method nên mô tả hành động hoặc dữ liệu, không dùng tên chung như Manager cho mọi thứ.

### Buổi 10: Bài kiểm tra chặng

App console hoàn thành cần có:

- Expense gồm id, category, amount và date;
- thêm, sửa, xóa, liệt kê, tổng theo tháng;
- lưu/đọc JSON;
- validation input và thông báo lỗi rõ;
- ít nhất 6 unit test có cả case hợp lệ và biên;
- README ngắn nói cách chạy, dữ liệu mẫu và quyết định định dạng tiền.

Đạt chặng khi bạn có thể mở một file bất kỳ và nói được nó thuộc trách nhiệm nào, dependency nào, và cách kiểm tra nó.
