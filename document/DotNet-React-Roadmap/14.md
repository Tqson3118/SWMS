# Chặng 14: Triển khai và vận hành

Thời lượng tham khảo: 4–5 tuần. Điều kiện vào: đã có application, test suite tối thiểu và README chạy được.

Chặng cuối của lộ trình này chưa biến Sổ chi tiêu thành hệ thống enterprise. Mục tiêu là deploy được một ứng dụng đơn khối có cấu hình tách môi trường, log hữu ích, health check, backup/restore và rollback. Sau khi làm tốt điều này mới học background jobs, Redis, queue, SignalR hoặc system design theo nhu cầu.

## Mục tiêu đạt được

- Đóng gói backend/frontend bằng Docker hoặc deploy provider có quy trình tương đương.
- Tách cấu hình dev/staging/production; secret không nằm trong image/repository.
- Bật HTTPS và kiểm tra CORS/refresh route sau deploy.
- Có structured log, correlation id và health checks.
- Biết metrics/tracing ở mức đọc request latency, error rate và dependency failure.
- Backup/restore được database học tập và thực hiện rollback có kiểm chứng.
- Viết runbook: deploy, kiểm tra, điều tra lỗi và quay về phiên bản trước.

## Tuần 1: build artifact và môi trường

### Buổi 1: build một artifact lặp lại được

Build phải dùng commit/version xác định. Ghi lại:

- SDK/runtime và package major.
- Lệnh restore/build/test.
- Environment variables bắt buộc nhưng không ghi giá trị secret.
- Database migration cần chạy ở bước nào.
- Static frontend gọi API origin nào.

Không build production bằng file source tùy ý trên máy cá nhân rồi upload thủ công mà không biết artifact được tạo ra thế nào.

### Buổi 2: Docker cho backend

Ví dụ multi-stage tối thiểu:

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src

COPY ExpenseApi.csproj .
RUN dotnet restore

COPY . .
RUN dotnet publish -c Release -o /app/publish --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:10.0 AS final
WORKDIR /app
COPY --from=build /app/publish .

ENV ASPNETCORE_HTTP_PORTS=8080
EXPOSE 8080
ENTRYPOINT ["dotnet", "ExpenseApi.dll"]
```

Tag image theo commit, không chỉ dùng latest. Không đưa appsettings có password vào image. Nếu provider dùng runtime khác, kiểm tra version thay vì copy Dockerfile mù quáng.

Bài tập: build image, chạy container với connection string/secret qua environment, gọi health endpoint và xem log.

## Tuần 2: config, HTTPS và CI/CD

### Buổi 3: cấu hình theo môi trường

Lập bảng:

| Giá trị | Local | Staging | Production |
|---|---|---|---|
| API URL | localhost | domain staging | domain thật |
| DB connection | local test | managed/test DB | secret manager |
| CORS origin | Vite dev | staging frontend | frontend thật |
| Log level | Debug có kiểm soát | Information | Information/Warning |
| Seed data | cho phép | có chủ ý | không seed demo |

Frontend VITE_ vẫn là dữ liệu client nhìn thấy; không đặt password/API secret ở đó. Backend đọc secret từ provider phù hợp.

### Buổi 4: pipeline deploy

Pipeline có thể theo thứ tự:

1. Pull request: format/lint/build/unit/integration.
2. Main branch: build artifact/image, scan dependency/image theo khả năng, publish.
3. Staging: migrate theo quy trình, deploy, smoke test.
4. Production: approval/rollout, health check, monitor.
5. Nếu fail: stop rollout hoặc rollback image/schema theo runbook.

Migration database là bước có rủi ro riêng; tránh deploy code cần column mới trước khi schema tương thích. Với thay đổi phá vỡ, học expand/contract: thêm mới tương thích, migrate data, đổi code, rồi mới dọn cũ.

## Tuần 3: health, logging và quan sát

### Buổi 5: health checks

Tách readiness và liveness trong cách suy nghĩ:

- Liveness: process còn chạy, không nên gọi dependency nặng.
- Readiness: instance có sẵn sàng nhận traffic và dependency cần thiết hoạt động không.

Health endpoint không trả connection string, stack trace hoặc thông tin nội bộ. Test endpoint khi database down và ghi expected behavior.

### Buổi 6: structured logging

Log event có field tìm kiếm được:

- request/correlation id.
- route/status/elapsed milliseconds.
- user id dạng an toàn nếu chính sách cho phép.
- dependency/database failure.
- import batch id hoặc idempotency key đã được che/mã hóa phù hợp.

Không log password, token, full note nhạy cảm hoặc raw connection string. Log không phải nơi duy nhất để lưu dữ liệu nghiệp vụ.

### Buổi 7: metrics/tracing ở mức thực dụng

Bắt đầu với bốn tín hiệu:

- request count.
- error rate.
- latency percentile.
- database/external dependency failure.

Tracing giúp nối một request qua API, service và database/dependency. Không thêm dashboard phức tạp trước khi có câu hỏi cụ thể: endpoint nào chậm, lỗi nào tăng, deploy nào gây regression.

## Tuần 4: backup, restore và rollback

### Buổi 8: backup/restore

Backup chỉ có giá trị nếu restore thử được. Với database học tập:

1. Tạo backup có timestamp/version.
2. Tạo database restore riêng.
3. Kiểm tra row count, một report quan trọng và migration state.
4. Ghi thời gian restore và điểm mất dữ liệu dự kiến.
5. Không overwrite database gốc khi đang học restore.

Bài tập: xóa một database test, restore từ backup và chứng minh expense/report còn đúng.

### Buổi 9: rollback

Rollback application không luôn đồng nghĩa rollback database. Nếu migration đã thay đổi schema, cần biết phiên bản code cũ có còn chạy với schema mới không. Viết runbook cho:

- image lỗi sau deploy.
- health check fail.
- query chậm.
- migration fail.
- dữ liệu bị ghi sai.
- dependency ngoài không phản hồi.

## Dự án chặng: deploy được và điều tra được

1. Containerize backend; build frontend artifact.
2. Cấu hình environment không commit secret.
3. Chạy CI quality gate từ Chặng 13.
4. Deploy staging hoặc môi trường tương đương.
5. Chạy smoke test login/list/create/report.
6. Bật structured log và health endpoint.
7. Tạo backup, restore vào database riêng.
8. Cố ý deploy một lỗi nhỏ, tìm qua log/health, rollback và ghi thời gian phục hồi.
9. Hoàn thiện README/runbook.

### Điều kiện đạt

- Một người khác có thể clone repository, đọc README và biết cách build/deploy.
- App không phụ thuộc file secret trong source.
- Health check và smoke test phát hiện backend/database không sẵn sàng.
- Có log đủ để tìm correlation/request và status/latency.
- Restore backup thành công trên database riêng.
- Rollback application được kiểm chứng; giới hạn rollback schema được ghi rõ.

### Checkpoint cuối lộ trình

Cụ nhận một yêu cầu mới và làm được chuỗi:

1. Phân tích domain/contract và rủi ro.
2. Chọn nơi sửa trong API/database/frontend.
3. Viết test case và dữ liệu biên.
4. Implement một vertical slice.
5. Chạy build/test/smoke test.
6. Deploy staging.
7. Quan sát log/health, xử lý lỗi hoặc rollback.
8. Giải thích quyết định và known limitations.

## Interview checkpoint

1. “Máy mình chạy, server lỗi”: cụ kiểm tra từ đâu?
2. Vì sao secret frontend không thể coi là bí mật?
3. Health check khác log ở điểm nào?
4. Rollback code có luôn rollback schema được không?
5. Vì sao tag image theo commit tốt hơn chỉ dùng latest?
6. Cần log field nào để điều tra request chậm?
7. Backup thành công có chứng minh restore thành công không?
8. CI nên chặn deploy ở bước nào?
9. Khi nào chọn monolith tiếp tục thay vì tách microservices?

Bài vận hành có thời gian 45 phút: deploy một phiên bản làm health check fail hoặc API trả 500. Cụ phải dùng runbook tìm log, xác định commit/image, rollback, chạy smoke test và ghi lại nguyên nhân.

## Tự chấm

- 0: chạy được local nhưng deploy thủ công, không có runbook.
- 1: deploy được nhưng config/secret/log còn lẫn lộn.
- 2: có pipeline, health/log/backup/restore/rollback smoke test.
- 3: điều tra được incident nhỏ, giải thích giới hạn rollback và đề xuất cải thiện dựa trên bằng chứng.

## Sau Chặng 14

Chỉ mở rộng khi monolith đã có lý do thật:

- Background jobs khi có tác vụ dài hoặc retry.
- Redis khi có nhu cầu cache/distributed state đo được.
- Message queue khi cần tách producer/consumer hoặc xử lý bất đồng bộ.
- SignalR khi sản phẩm thật cần realtime.
- System design khi cụ đã mô tả được traffic, consistency, failure và vận hành của hệ thống hiện tại.

Microservices, Kubernetes và DDD sâu không phải checkpoint bắt buộc trước khi cụ làm tốt một ứng dụng đơn khối.
